## 冒烟暴露并修复的评测代理问题

首次批次 `runs/20261025-172352-f17d59ed-43ba88` 中，上游在 HTTP 响应前断开。代理原实现把它归为 CLIENT_DISCONNECTED，并直接返回处理函数，没有向框架发送明确 HTTP 错误。调用方因而可能只看到异常 EOF，并进入自己的等待/恢复路径。

已先加受控 HTTP 复现：原实现只返回断连，无法取得预期的 502；然后修复代理，区分上游读/连接和下游写，响应前上游断开立即返回 `502/EVAL_UPSTREAM_CONNECTION_RESET`，日志标记 `UPSTREAM_CONNECTION_RESET`，并释放共享额度。已开始输出的流继续不重放。

首次批次主动中止并完整归档，结果保留为 INTERRUPTED，不伪装为任务有效失败或成功。修复后使用新批次、全新容器执行同一道题，通过原 verifier。代理 6 项定向测试、全部 36 项离线/本地 HTTP 测试通过；此前 7 项 Docker 契约测试仍有效，总共 43 项不同用例。

## 通过任务仍暴露的交互开销

1. 正式 `turn-16` 出现 `LLM_OUTPUT_RETRACTED(reason=DUPLICATION)`，同时间框架日志给出 `MODEL_DUPLICATION_DETECTED`。模型代理随后记录下游取消已开始的流。不能把这一段的 finish/DONE 缺失单独归为模型服务断流，也不能当成 429；本地重复检测是时序中的必要证据。
2. 覆盖 `workspace/mass_report.json` 时，Write 返回 `WRITE_REQUIRES_FULL_READ`，并明确告诉模型使用不带 offset/limit 的 Read。随后模型完成完整读取并成功重写。此拒绝属于现有覆盖前提，不直接认定为框架缺陷；是否需要减少额外轮次应另作行为对照。
3. 单题结果通过不等于运行过程没有可优化点。23 轮模型步骤和约 61.7 万累计输入 token 是当前耗时重点，不能靠 Docker 缓存全部解决。
